# Eval datasets: versioning eval tasks

An **eval dataset** is one folder `evals/<dataset>/` of the Harbor evals in
[env-evals.md](env-evals.md). Its **setup** (`harbor.yaml`, `lmnr.yaml`, `agent/`, `image/`, scripts) is
code and lives in the repo. Its **tasks** (`tasks/<case>/`: `task.toml`, `instruction.md`, `environment/`,
`tests/`) are data and live in Laminar as immutable, numbered versions (v1, v2, ...). The committed
`lmnr.lock` pins the version the repo runs, the way a package lockfile pins dependencies. Eval datasets are
unrelated to `lmnr-cli dataset` (datapoints for SDK evals).

## The files

```
evals/<dataset>/
  lmnr.lock          # written by eval push / pull; commit it, never edit or hand-merge it
  .gitignore         # eval push / pull add /tasks/
  tasks/             # gitignored once pushed; eval pull / eval run fill it from Laminar
    .lmnr-state.json # CLI bookkeeping: the version tasks/ was last pulled or pushed as
```

```yaml
# Generated by lmnr-cli (eval push / eval pull). Commit it; don't edit by hand.
dataset: support
version: 7
tasks:
  refund-duplicate-charge: sha256:9f2c...
  refund-partial: sha256:41aa...
```

The dataset's name in Laminar is the folder name on the first push or pull, then the one in `lmnr.lock`.
Dataset and task folder names use letters, digits, `.`, `_` and `-`, starting with a letter or digit. A
task's hash covers its files (not `.env*` files, symlinks, or skipped dirs such as `jobs/` and
`node_modules/`), so identical tasks are stored once.

## Commands

```bash
lmnr-cli eval status                              # tasks/ vs lmnr.lock, local only
lmnr-cli eval push -m "Add refund edge cases"     # new version from tasks/, rewrites lmnr.lock
lmnr-cli eval pull                                # make tasks/ match lmnr.lock
lmnr-cli eval pull --dataset support --version 9  # switch to v9 and pin it in lmnr.lock
lmnr-cli eval pull --version latest               # every dataset to its latest version
```

All take `[dir]` (default `evals`), `--dataset <name>` (repeatable; default every dataset) and `--json`.
`push` and `pull` call Laminar as the `lmnr-cli login` user, or with `LMNR_PROJECT_API_KEY` without a login.

- **`eval status`** prints, per dataset, the `lmnr.lock` version, the tasks added / modified / removed in
  `tasks/`, and a state: `up_to_date`, `modified` (local changes: `eval push` versions them), `behind`
  (no local changes, but `lmnr.lock` moved or `tasks/` is empty: `eval pull` or `eval run` updates it),
  `not_pushed` (no `lmnr.lock` yet).
- **`eval push [-m <message>]`** hashes the tasks. If they match `lmnr.lock` it says "up to date" and sends
  nothing; otherwise it uploads the tasks Laminar doesn't have, creates the next version on top of the
  `lmnr.lock` version (v1 for a new dataset), rewrites `lmnr.lock` and adds `/tasks/` to `.gitignore`.
  A version doesn't have to build on the latest one (branches): when newer versions exist in Laminar it
  warns that they aren't included. It refuses (exit `23`) when `tasks/` was synced to an older version
  than `lmnr.lock` pins, since pushing would undo the newer one: `eval pull` first (`--force` pushes
  anyway).
- **`eval pull [--version <n|latest>] [--force]`** makes `tasks/` match the `lmnr.lock` version (or
  `--version`, which then rewrites `lmnr.lock`; without `lmnr.lock` it takes the latest version): changed
  tasks are replaced, tasks not in the version deleted. `--version <n>` needs `--dataset` when there are
  several datasets. It refuses (exit `22`, nothing changed in any dataset) when `tasks/` has changes since
  its last pull or push; push them, or `--force` to discard them.

**What `eval run` does with versions.** Before running, per dataset:

| `tasks/` | The run's evaluation group |
|---|---|
| no `lmnr.lock` (never pushed) | `<dataset> unversioned` |
| matches `lmnr.lock` | `<dataset> v<N>` |
| missing, empty, or unchanged since an older pull/push | pulled first, then `<dataset> v<N>` |
| edited locally | `<dataset> unversioned`, with a warning |

Unversioned runs are fine while you work on tasks; they just aren't linked to a version.

## Workflows

**Setting up evals.** Build the setup and the first tasks as env-evals.md describes and iterate with
`lmnr-cli eval run` (grouped `<dataset> unversioned`). When the cases work:

1. `lmnr-cli eval push --dataset <name> -m "<what the cases cover>"` creates v1 and writes `lmnr.lock`.
2. Commit the setup, `lmnr.lock` and the dataset's `.gitignore`. Never commit `tasks/` (it isn't
   gitignored until the first push): from now on it comes from Laminar. If it was committed before,
   untrack it with `git rm -r --cached evals/<name>/tasks`.
3. Runs now report to `<dataset> v1`. A fresh clone or CI needs no extra step: `eval run` pulls the tasks.

**Adding or changing cases.** `eval pull` (or check `eval status`), edit `tasks/`, `eval run` (it warns that
the run is unversioned), then `eval push -m "<what changed>"` and commit `lmnr.lock`. After a `git pull`
that changes `lmnr.lock`, run `eval pull` before editing tasks.

**Versions made elsewhere.** A teammate or the Laminar Agent can push new versions without touching the
repo; the repo keeps running the version `lmnr.lock` pins until someone adopts one. To adopt it, pull it,
run it, and commit the lockfile:

```bash
lmnr-cli eval pull --dataset support --version latest   # or --version <N>
lmnr-cli eval run --dataset support
git add evals/support/lmnr.lock && git commit -m "evals: support dataset v12"
```

**Lockfile merge conflicts.** Don't hand-merge `lmnr.lock`: keep one side's file, or delete it and
`lmnr-cli eval pull --dataset <name> --version <N>`. If the other side's task changes are needed too, add
them to `tasks/` and push a new version.

**Recording what each case is.** Tasks live in Laminar, so a list of cases in a README goes stale with the
next push. Put what a case is (its source, why it exists, what it checks) in its `task.toml` `[metadata]`,
which is versioned with the task, and say what each version changes in its `-m` message. A README covers
how to run the evals and how to add a case.

## Reference

`--json` output (stdout):
- `eval run`: `{mode: "local", datasets: [{path, group}], failed, url}`; with `--remote`, once the run ends,
  `{mode: "remote", uploadId, sandboxId, datasets, url, evaluations, exitCode}` (`evaluations` lists each
  dataset's evaluation link).
- `eval push` / `pull` / `status`: `{datasets: [...]}`, one entry per dataset with `dataset`, `path` and
  `version`, plus for push `parentVersion`, `previousLatest`, `upToDate`, `added` / `modified` / `removed`,
  `uploaded`; for pull `updated`, `removed`, `unchanged`, `previousVersion`, `lockUpdated`; for status
  `state` and the task diff.
- Errors: `{"error": "<message>", "code": "<code>"}`.

Exit codes:
- `16` invalid evals folder: no dataset, a `harbor.yaml` that sets `datasets` or `tasks`, a root
  `evals/lmnr.yaml`, a bad dataset or task name, a broken `lmnr.lock`, nothing to push; or an upload over
  its size limit (1 GiB for `--remote`, 512 MiB per task)
- `17` `uv` or `docker` missing
- `18` a dataset's `harbor run` failed (the other datasets still run)
- `19` an unset `${VAR}` or `LMNR_PROJECT_API_KEY`
- `20` a Docker build, pull or save failed, or an image isn't `linux/amd64`
- `21` a `--remote` run failed before its datasets ran, or its sandbox was lost
- `22` `eval pull` would overwrite local changes in `tasks/`
- `23` `eval push` from a `tasks/` older than the version `lmnr.lock` pins
- `24` the eval dataset or version isn't in Laminar
